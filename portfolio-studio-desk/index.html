Portfolio website

A portfolio that connects my work to the skills behind it, with a custom editor for keeping it up to date.

Design

A portfolio that connects my games, films, artwork and software to the skills behind them. Visitors can follow a role to a skill, then open a project or a specific case-study section showing where I used it. I also added a custom browser-based editor, called Studio Desk, so I can keep the content, presentation and project relationships up to date myself.

Technical

The portfolio and its editor run on GitHub Pages, with no separate application server to maintain. The editor uses the GitHub API for private drafts and static publishing, and shares its page-rendering code with the public site. Content editing, previewing and publishing happen in the browser.

Product definition

A home for the work, and a clearer way to explain it

I make games, films, illustrations, animations and software. My bio site brought those links together, but it left visitors to work out what connected them and what I contributed. I wanted a portfolio that could answer those questions without asking everyone to read my entire history.

I also find it difficult to pitch myself. Imposter syndrome makes choosing a title uncomfortable when my work crosses several disciplines. Following a title back to something I have made gives me a concrete starting point for that conversation. It also helps me recognise the work for myself.

The brief had two audiences. A recruiter needs to understand the work quickly and find relevant examples. I need to keep adding and refining those examples without turning every update into another development task. The public portfolio and its custom editor grew together around those needs.

Cost and independence shaped the scope: a public site on GitHub Pages, an editor I can open independently of the original build environment, and private drafts that stay separate from published content. Project overviews could go live before their longer case studies were ready. That made the portfolio useful while leaving room for the writing to grow.

Visual design

A consistent frame for very different kinds of work

My projects look very different from one another, so the website needs to give them a consistent home without competing for attention. The pale and dark backgrounds let the artwork stand out. A faint square grid, clear borders and small coloured squares give the pages a recognisable style without adding another large image or texture behind the work.

The site uses two fonts, each with a different job. Space Grotesk is the main reading font, used for headings and paragraphs. The large introduction makes the changing role easy to notice. JetBrains Mono distinguishes navigation and labels from the main text, helping people recognise what they can use to move around the site. If either font cannot load, the browser can display a standard alternative.

One highlight colour ties the site together, appearing in the changing role, buttons and smaller details. The highlight colour stays consistent in light and dark modes, while the background and text change around it. I wanted both versions to feel like the same website. Each colour option still needs to be checked against both backgrounds, because a colour that stands out on black can be difficult to read on white.

The homepage introduces me beside a portrait card, then shows a small selection of projects and a link to the complete collection. Spacing makes that order easier to follow: the introduction, featured work and next step each have room to be noticed. On a phone, the portrait moves below the introduction, while my name and the navigation stay together at the top.

Project pages open with enough context to understand the work before the longer explanation begins. A narrower text column keeps long paragraphs easier to read, and the section menu lets visitors choose what interests them. Headings name the subject, subheadings explain what the section covers, and screenshot captions point out the detail worth looking at.

Content design

From a role to an example of the work behind it

A single job title would leave out too much of my practice. Showing every title at once would make the introduction hard to read. The rotating role creates one readable entry point at a time, and each title links to its corresponding skill on the “Skills” page.

The route is concrete: click a role, arrive at its highlighted skill, then choose a project dot. A dot opens the relevant published case-study section when one is available, or the project overview otherwise. Visitors can also ignore the roles and go straight to “Work”.

The titles come from the skills data and only appear when they have published project evidence. Random selection gives more weight to skills with more linked evidence, so the introduction responds to the work I have documented. This is a way to vary what visitors encounter, not a measurement of ability or importance.

Plain language matters here. A title should tell someone what I do, rather than require them to interpret an impressive-sounding label. I can edit role names and timing in the editor, and visitors can pause the rotation or use the arrows to explore at their own pace.

Information architecture

Two routes into the same body of work

“Work” groups projects by discipline. “Skills” groups individual skills into broader areas without merging them into vague combined labels. Those routes serve different questions: what have I made, and where have I used a particular skill? Both lead to the same project pages.

The dots are evidence links, not proficiency ratings. Hovering over a dot or focusing it with a keyboard reveals the project name. Section destinations bring a visitor to the relevant explanation with a visible scrolling transition, rather than leaving them to search a long page.

Each project starts with its category, title, one-line premise, media and summary. The “My work” section sits separately, with contribution tags linking back to “Skills”. This distinguishes what the project is from what I did on it, particularly for collaborative films and games.

A short overview can remain public while its longer case study is still being written. Category labels, section navigation and next-project links keep the route onward visible. The next-project sequence follows the category order in the editor, so reorganising the collection also updates its navigation.

Interaction design

Useful feedback, stable navigation and room for play

I wanted the site to feel satisfying to use, but interaction should help people explore the work. One early menu exposed the difference: expanding a category pushed the categories below it away from the pointer. Moving downward could land on the wrong item.

The revised “Work” menu opens projects in a neighbouring panel, keeping category targets in place. Hovering a category reveals its panel without accumulating an increasingly tall list. Up to six projects appear before an “And more” link, or “View category” when the list already fits.

Hover, keyboard focus and pressed feedback give controls a visible response. Panel transitions and the small animated square beside my name add continuity, while the same arrow style connects navigation and media controls. Those details belong to one interaction language instead of competing for attention.

Larger project categories used to dominate the “Work” page. They now become looping carousels when their cards exceed the available slots: up to three on desktop and one on narrow screens. Arrow clicks advance one card. Dragging or swiping adds momentum, while holding an arrow continues movement. Short groups remain ordinary rows.

Still thumbnails give the collection a calmer starting point, with motion previews where available. Project media carousels combine screenshots and moving images with captions. Centring images within the frame accommodates posters as well as landscape game screenshots without leaving a portrait image awkwardly aligned to one side.

The portrait card adds a more playful interaction. Clicking or tapping flips it once. A drag or swipe spins it according to the gesture, and another gesture can interrupt or reverse it. Earlier versions spun on hover and felt distracting, so the card now stays still until deliberately engaged.

Discoverability needed its own compromise. A hint appears on hover or keyboard focus, and briefly on touch screens when the card enters view. People can find the interaction without having a permanent instruction compete with the introduction.

Accessibility considerations

Control over movement and alternatives to gestures

Movement should not be a condition of reading the site. Roles can be paused or stepped through manually, thumbnail previews have playback controls, and reduced-motion preferences simplify animated interactions. The portrait stays still on hover.

Visible focus indicators, descriptive control labels and a skip link support keyboard navigation. Skill-dot tooltips appear on focus as well as hover. Carousel arrows and keyboard controls provide alternatives to dragging, and off-screen cards are removed from the tab sequence until they become visible.

Responsive layouts do more than shrink the page. Navigation, skill rows, reading columns and project cards rearrange to preserve their relationships. A section sidebar, floating back-to-top control and a subtle bottom fade help people orient themselves on long case studies. The fade disappears at the end of the page.

These controls give visitors more than one way to explore: keyboard navigation alongside gestures, still images alongside motion, and direct section links alongside ordinary scrolling.

Systems design

An editor built around the way this portfolio grows

Studio Desk is the custom editor for this website, rather than an existing product visitors are expected to know. I think of it as a personal “Squarespace” of sorts: I can manage projects, write copy, upload media and arrange supported content blocks without editing source files for each update.

The editor manages relationships as well as words and images. Featured selections, category order, contribution tags and skill destinations feed the public pages. Keeping those choices in one content model reduces the number of separate places I need to remember to update.

Project controls cover the overview, contribution tags, media, captions, dated statistics and longer case study. Text, images, galleries, quotes and other supported blocks can be reordered. This gives me flexibility within a consistent page structure, rather than requiring a new layout for every project.

The preview updates as I edit, with desktop and mobile views and a light/dark switch. It uses the same page-rendering code as publishing, reducing the gap between the editing view and what visitors receive.

A fixed homepage screenshot became misleading when I changed palettes. The portfolio card now uses a small rendered representation of the homepage that follows the current content and colours. Screenshots inside this case study remain historical captures, so their colours may differ from the theme you are browsing today.

Technical specification

Static publishing with private drafts and clear boundaries

The published portfolio is static HTML, CSS and JavaScript hosted on GitHub Pages. Its pages do not need an application server to assemble their content for each visitor. The browser-based editor uses the GitHub API to store content and generate the files that are published.

Private draft storage and the public website are separate. Saving a draft does not immediately change the live pages, and an overview can be published while its case-study sections remain private. The export excludes unpublished sections and media used only by those sections.

Publishing controls distinguish a live site that matches saved content from one with unpublished changes. I can also take the portfolio offline while retaining access to its editor. Previously published material can still exist in caches or copies.

Editor updates can be installed separately from content updates, so improving the tools does not require publishing content changes. Newer-draft checks and conflict handling address another practical risk: editing in an older tab should not silently overwrite more recent work. Backups provide another recovery route.

Saved connections can be encrypted on the device and unlocked with a password, avoiding repeated token entry. The credentials still belong to the services they access, and clearing browser storage removes that saved connection. A static public site does not make private drafts or API tokens public content.

The wider setup also includes a GoatCounter analytics view and a refresh control for a separate project-progress dashboard. These integrations rely on external services and GitHub workflows. “No separate application server” describes what I maintain for the portfolio, not an absence of service dependencies.

Iteration

What changed through use

Using the portfolio exposed problems that a static mock-up would have missed: moving menu targets, accidental portrait spins, overflowing project groups and previews that stopped matching the selected palette. Each revision connected a visible problem to a specific change rather than adding interaction for its own sake.

The result is a place where my work can be explored through projects or skills, with an editor that lets me keep developing the content myself. The same project can support several skills, while each link gives visitors a concrete example to explore.
